# BatchGet 双进程连续吞吐测试汇总

整理日期：2026-09-15。数据来自本次实验会话提供的 13 组不同配置日志，编号沿用 A～M；重复发送的相同日志不重复统计。编号按会话中的归档顺序排列，不代表严格的执行时间顺序。

本文汇总连续吞吐 benchmark；前期逐批 kernel profile、双 stream 延迟测试以及口述的单进程补测采用不同口径，不并入下方总表。

## 1. 当前结论

1. **两进程在每进程 1 核、1 Jetty 时，可以接近独立运行预期。** B、F 组各自独跑约 25 GB/s，并发达到 45～47 GB/s，达到等工作量独立运行参照的 91%～94%。
2. **共享 CPU EID 时，严重退化跨 device 仍然存在。** L、M 分别为同 device 和跨 device，使用两个不同 CPU 服务、相同 CPU EID，聚合只有 30.16、31.89 GB/s；各路独跑均约 45 GB/s。
3. **分开 CPU 服务/EID 后，严重退化明显缓解。** 在相同核/Jetty 配置下，L→H 从 30.16 提高到 42.82 GB/s，M→I 从 31.89 提高到 47.58 GB/s。证据指向远端端点关联的资源、路径或服务配置，但尚未唯一定位到 CPU EID、网口或 DDR 中的某一个部件。
4. **核数和是否同卡，不能单独解释全部现象。** J/L 保持 4 Jetty、改变总核数，均约 30.1 GB/s；I/K 在两个 device 上同样保持 4 Jetty、改变总核数，均约 47.6 GB/s。
5. **约 43～48 GB/s 是部分配置下观察到的聚合平台，尚不能认定为物理带宽上限。** 两个 CPU 服务始终位于同一台 CPU 主机；CPU 内存、网络和提交主机等共享资源尚未隔离。

需要分开解释两个现象：一是共享 CPU EID 的部分配置下约 30～33 GB/s 的严重退化；二是分开 CPU EID 后约 43～48 GB/s 的聚合平台。它们不等于已经确认了两个独立的硬件瓶颈。

I、K 组已完成全部测量及校验，但最终退出超时。其吞吐可以按 RESULT 重算并参与性能对照，整体运行状态仍标记为异常。

## 2. 测试方法与统一参数

入口：`tests/python/test_npu_batch_get_throughput.py`。每组创建两个独立进程，各自持有 Runtime、远端表、请求库和输出。每个进程始终为 1 stream、1 transport；本报告中的“双进程”不表示对同一个 Runtime 进行并发调用。

两个进程都初始化、预填表、生成请求并预热后，依次执行 `solo_0`、`solo_1`、`concurrent` 三类阶段。每类测量 3 次，每轮轮换阶段顺序；独跑阶段另一进程保持空闲。因此“独跑”是在另一个进程已经初始化的实验环境中执行，并非重新启动一个完全独立的单进程环境。

| 参数 | 所有组的值 / 含义 |
| --- | --- |
| `process_count` | 2 |
| `stream_count` / `transport_count` | 每进程均为 1 / 1 |
| `token_bytes` | 656 B |
| `miss_count` | 每进程每批 8192 次读取 |
| `request_length` | 每进程 32768，表示请求数组和输出容量，不是每批实际读取数 |
| `iterations` / `repeats` | 每阶段每进程 20000 批 / 3 轮 |
| `request_bank_size` | 每进程预生成 64 组请求，计时内轮换复用 |
| `table_capacity` / `tokens_per_block` | 每进程 1277952 条表项 / 每条 128 个 token |
| 每进程远端 region | 107307073536 B，约 99.9375 GiB |
| `warmup` / `populate_chunk_entries` | 16 / 128 |
| `seed` | 20260915，各进程实际种子为 `seed + rank` |
| 请求排列 | 随机请求，`sort_input_indices=false` |
| kernel profile | 关闭 |
| 超时设置 | 协调阶段 `timeout_seconds=600`；最后等待子进程退出另有固定 5 s 检查 |

单批有效载荷为 `8192 × 656 = 5373952 B`。每个独跑测量窗口读取 `107479040000 B`（107.47904 GB）；每个并发测量窗口两进程合计读取 `214958080000 B`（214.95808 GB）。每个进程读取相同工作量，并发阶段的总工作量是独跑阶段的两倍。

预填表、请求生成/排序、输出注册、前置校验和 warmup 均在计时外。计时内连续异步提交 20000 批，最后同步一次；没有逐批 profile 回读、请求生成、校验或打印。快进程测量结束后等待，直到所有活跃进程结束测量，才开始后置校验。

### 2.1 计时与带宽口径

所有 GB/s 均为十进制。单个测量窗口使用同一主机的单调时钟：

```text
公共窗口 = max(所有活跃进程 end_ns) - min(所有活跃进程 start_ns)
聚合吞吐 = 所有活跃进程有效载荷字节数之和 / 公共窗口
三轮汇总 = 三轮有效载荷字节数之和 / 三轮公共窗口时长之和
```

三轮汇总不是三轮 GB/s 的算术平均。结果包含主机提交、可能的提交背压、设备执行和最后排空，不能解释为纯 kernel 执行时间或物理链路忙碌时间。`submit_ms` 与设备执行可以重叠；提交耗时长本身也不能证明 Python/CPU 是瓶颈。

总表的两个比值定义如下：

```text
相对最快独跑 = 并发聚合吞吐 / max(独跑 0 吞吐, 独跑 1 吞吐)
独立运行参照 = 2 × min(独跑 0 吞吐, 独跑 1 吞吐)
独立参照达成率 = 并发聚合吞吐 / 独立运行参照
```

独立运行参照假设两路保持各自独跑速度。因为两路读取相同字节数，较慢一路决定整体完成时间，所以参照值不是直接将两个独跑 GB/s 相加。它是本实验的对照指标，不是硬件利用率，也不是物理最大带宽。

`host_window_overlap_fraction` 衡量两个主机测量窗口的交集/并集。它可以揭示开始错开和完成长尾，但不证明 kernel 或物理传输实际同时发生。各 worker 的 `common_window_GBps` 使用同一公共窗口；工作量相等时这两个值自然相等，不能据此断言两个进程自身速度相同。

## 5. 关键对照矩阵

下列四组每进程均为 **1 核 × 2 Jetty**，并发总计 **2 核、4 Jetty**，CPU 服务都在 `.73` 主机上：

| CPU 端配置 | 同 device 0、同 NPU EID N2/N2 | 跨 device 0/1、各自 NPU EID N2/N3 |
| --- | ---: | ---: |
| 不同服务、相同 CPU EID：S2/S4 | L：**30.16 GB/s** | M：**31.89 GB/s** |
| 不同服务、不同 CPU EID：S2/S3 | H：**42.82 GB/s** | I：**47.58 GB/s**† |

这张矩阵是当前最直接的端点/设备对照：仅换到另一个 device 并没有消除共享 CPU EID 场景的严重退化；更换第二个 CPU 服务及其 CPU EID 后，两种 device 配置均明显改善。

但它仍不等于“只改变 CPU EID 位值”的实验：S3/S4 是不同服务，远端内存分配、NUMA 放置和相关通信资源没有被独立记录或固定；跨 device 同时更换了本端 EID。矩阵支持定位方向，尚不能唯一归因到某个硬件部件。

上述百分比均由未四舍五入的三轮汇总值计算。跨组对照按显式配置说明变化，不能据此假定后台负载、页模式、内存放置及其他环境状态完全一致。尤其 A～C 与 D～M 使用不同 CPU 主机，不应直接用跨主机的吞吐差值给单一因素定性。

### 6.1 当前不能得出的结论

- 不能认定“总共 4 Jetty 是所有配置通用的硬阈值”。相同 4 Jetty 在不同端点/设备组合下表现从约 17 到 48 GB/s 不等。
- 不能认定“不同 NPU EID 一定会使带宽叠加”，也不能认定“CPU 服务进程分开就足够”。G/H 及 J/L/M 都提供了相反的配置实例。
- 不能认定“已经达到单张 NPU 卡、CPU DDR 或某个网口的物理带宽上限”。当前只有有效载荷的主机窗口吞吐，没有对应硬件计数器或链路容量验证。
- 不能把 EID 当作物理资源隔离证明，或把 `submit_ms` 的增长直接认定为 CPU 提交瓶颈。
- 不能完全排除 AIV/CQ 路径的影响；现有实验只是削弱了“4 个核同时轮询是必要原因”等简单解释。

## 7. 数据有效范围与退出异常

每组 3 类阶段、每类 3 次，共 9 个测量窗口；13 组共有 117 个窗口。所有日志窗口均标记 `postflight_pass=true`，各进程前置检查了 64 组请求计划。

计时内反复覆盖同一个输出，后置校验只检查最后一组请求对应的结果；没有保存并逐批验证所有中间输出，也没有逐批读取 kernel 状态。因此“校验通过”应按这套检查范围理解，不能扩大为每一批完整历史结果均已验证。

远端各 entry 沿用相同 token 内容模式，请求库也固定轮换复用。结果代表该请求模式和数据布局下的读取吞吐；更换请求库规模、数据模式、token 大小、NUMA 放置后需要重新测量。

I、K 没有打印 SUMMARY，错误分别为：

```text
I: BATCH_GET_THROUGHPUT_FAILED worker pid=156040 exitcode=None
K: BATCH_GET_THROUGHPUT_FAILED worker pid=159521 exitcode=None
```

按当前脚本，父进程收到所有 worker 的 `stopped` 消息后，调用 `process.join(timeout=5)`；检查时 `exitcode=None` 表示子进程仍未退出。此时所有计时窗口和后置校验已经结束，最终退出检查和清理不计入吞吐窗口。错误不等同于测量阶段 kernel 失败，但整体运行并未成功结束，具体退出阻塞点仍未确定。

本文按原始 RESULT 重算 I、K 的汇总，保留异常标记；其余组同时核对重算值与原始 SUMMARY 一致。正式复测仍应保留退出状态，并补充退出诊断或可配置的退出等待。

## 8. 后续优先验证方向

1. **核对 CPU EID 关联的资源和远端内存放置。** 记录 S2/S3/S4 对应的物理端口、通信资源、NUMA 节点，以及服务的 CPU/内存绑定和页模式。固定这些条件，对 L/H、M/I 的端点差异做重复对照，避免只凭 EID 字符串归因。
2. **两台独立 CPU 主机的对照。** 保持两个 NPU device、每进程资源和负载一致，分别连接两台 CPU 主机；使用该次实验重新测得的两路独跑速度计算参照，不能沿用当前约 90 GB/s 作为固定目标。
3. **在计时区间采集共享资源证据。** 对照独跑/并发的 CPU DDR 和网络/URMA 计数器、NPU 设备时间线与提交主机负载。区分链路/内存字节带宽限制、请求处理能力、提交断档及其他争用。
4. **在路径和资源放置固定后，再改变负载。** 分别改变 token 大小和请求数量，检查平台更接近字节吞吐还是请求速率限制；同时控制总工作量、远端表占用和请求库工作集，避免多个因素混变。该项属于后续实验，当前数据尚不能给出结论。
